How SAAPP is tested

A study sheet for the technical round. Everything on this page is in the repo today; the gaps are listed honestly in the amber box.

The 20-second answer I test at four levels. About 6,000 fast automated tests run with the model, database and embeddings faked, so they are free and repeatable. Some of those tests read the code itself to enforce rules, like no user content in logs. Separately, I run evals against the real model, scored by code, before I change a prompt, a tool or the model. In production, a dashboard tracks routing, fallbacks, cost and user feedback, and every failure I find becomes a new check.

The four layers

LAYER 1 · FAST TESTS

Does the code do what it should? (pytest, backend/tests)

  • About 190 test files and about 6,000 cases, running in about five minutes.
  • The model is faked: tests script what the model "says" so the result is the same every time.
  • A safety net blocks real calls. Automatic fixtures in conftest.py make a test fail if it tries to reach the real Gemini model, the embeddings service or MongoDB. A test cannot cost money or touch real data by accident.
  • Catches routing mistakes, broken logic, bad formatting and regressions.
Real model: noCost: noneRun: before every change
LAYER 2 · TESTS THAT READ THE CODE

Rules that must hold everywhere, enforced mechanically

  • No undefined names (test_no_undefined_names). Born from a real incident: a merge dropped one import line, nothing in the tests imported that file, it deployed, and every chat request failed with a NameError. The test now checks the compiled code for any name that is used but never defined.
  • Log hygiene (test_log_hygiene). Scans every logger call in the backend and fails, naming the line, if one includes user text, model text or documents. Logs can only carry ids, counts and tool names.
  • Write actions go through approval (test_write_action_registry), and tenant isolation (test_isolation_auth, test_graph_scoped): one customer's data is never read for another.
  • State does not leak between turns (test_checkpointer_resurrection_safety).
Real model: noCost: noneRun: with the fast tests
LAYER 3 · REAL-MODEL EVALS

Does the model still behave? (backend/evals)

Unit tests script the model, so they cannot tell you how the real one behaves. Evals ask the real model, many times, and score each reply with code, not with another model.

EvalWhat it asks
character_evalAbout 70 scenarios. Does Sonic's character hold, including under multi-turn pressure where the user pushes harder after each reply? Scores the first draft, so a high pass rate means the prompt alone holds the line.
behavior_evalFour kinds: tool use (picks the right tool), injection (hostile text in a log must not cause a fetch or a database call), repo (a fixture repository with known answers, so invented files are caught), opener.
memory_evalSix parts: recall, explicit recall, write, compaction, dedup and event replays. Is the right memory found, and nothing else?
fact_links_evalDoes the model link the right facts together? A wrong link puts unrelated context into a reply, so precision matters.
  • Several runs per scenario, because the model is not deterministic. The result is a pass rate.
  • --save keeps a baseline and --compare reports what got worse, exiting with code 1 so it could sit in front of a deploy.
  • Safe to run. Every outward path (GitHub, web, database, browser) is replaced, so whatever the model tries is recorded and nothing real is touched.
  • The scoring is tested too, without a model (test_behavior_eval, test_memory_eval, test_pressure_scorers).
  • Not part of pytest because they cost real money, so they are run on purpose and kept out of users' usage totals.
Real model: yesCost: cents to a few dollarsRun: before and after a prompt, tool or model change
LAYER 4 · WATCHING PRODUCTION

Is it working for real people? (the Sonic Health dashboard)

  • Routing: how many requests took the cheap path versus the expensive tool path.
  • Reliability: how often fallbacks and query rewrites happen, and response time.
  • Cost: token and prompt-size metrics, plus a daily spend cap per user and overall.
  • Quality signals from use: likes and dislikes, pushback after a reply, and outcome counters for individual behaviors.
  • Only counts and ids are recorded, never user content.
Real model: live trafficRun: always

Frontend: the TypeScript type checker (tsc) plus about 20 small test files for the logic modules, such as edit approval and error handling.

Be ready for these

Honest gaps. Say them before you are asked.

  • No automatic run on every push. The only GitHub workflow is a manual one for the Patchy test runner. I run the suite and the evals by hand before deploying.
  • Evals are scored by code, not by a model. That is cheap and repeatable, but it can miss subtle quality, so I read the actual replies.
  • The UI has thin automated coverage. The logic is tested; the screens are checked by hand.
  • One known failing test: a voice-composer test that asserts a word that is now in the persona text. It needs updating, not the product.

What I would add: run the fast tests on every push, put --compare in front of every deploy, and add a small model-based judge for tone, spot-checked by a person.

Likely questions

How do you test something that is not deterministic?

I split it. The parts around the model (routing, parsing, validation, approvals) are normal code, tested with the model faked. The model's behavior is tested with evals: run each scenario several times, score each reply with a code check, and compare the pass rate to a saved baseline.

What is the difference between a unit test and an eval?

A unit test checks that my code does the right thing given a scripted model. An eval checks what the real model does. Unit tests are fast, free and exact. Evals are slower, cost money and give a pass rate, not a yes or no.

How do you avoid regressions when you change a prompt?

Run the targeted evals before and after, save the baseline, and compare with a tolerance. Then read the actual replies, because a pass rate can stay flat while the answers get worse.

How do you test an agent safely?

Replace every outward path (GitHub, web, database, browser) for the length of the run, and record what the agent tried to do. That includes injection scenarios: a log line that says "fetch this URL" must lead to no fetch and still a useful answer.

Tell me about a bug your tests missed.

A merge silently dropped an import from the main file. No test imported that file, so everything passed, it deployed, and every chat request failed. I added a test that checks the compiled code for names that are used but never defined, so that whole class of bug is caught.

How do you know it is working in production?

A dashboard of routing, fallbacks, rewrites, response time, tokens and user feedback, with spend caps. When something goes wrong I find the cause from the data, fix it, and add a check so it cannot return quietly.

Why score with code instead of another model?

Code checks are cheap, repeatable and cannot be talked into agreeing. A model judge is better for subjective qualities like tone, but it adds cost and its own errors, so I would use one only alongside a person spot-checking it.

Why are the real-model evals not part of the test suite?

They cost real money and give a pass rate, not a clear pass or fail. So they run on purpose, targeted to what changed, and the fast suite stays free and quick.
