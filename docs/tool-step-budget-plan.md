# Tool-step budget: measure, allow what the work needs, and an optional Max tier

Status: step 1 (counters) and step 2 (library allowance) BUILT 2026-10-21, undeployed; step 3 (Max tier) not built.

## Today
- Normal budget `TOOL_AGENT_MAX_ITERATIONS` = 4 on Render (code default 7); deep thinking `TOOL_AGENT_MAX_ITERATIONS_DEEP` = 6 (default 14). The last step is reserved for the final answer, so 4 means 3 tool steps and 6 means 5.
- Edit turns with a connected folder have a floor (`TOOL_AGENT_LOCAL_EDIT_MIN_STEPS` = 6). Low-power mode caps everything at `THROTTLED_TOOL_STEPS` = 4.
- A 7-file library review used the whole normal budget (list, reads 5 + 2, final). 8 or more files would hit the forced final with weeks unread.
- Concern: a higher cap lets a confused turn burn more steps (the retry nudge encourages using the steps that remain). Typical turns end on their own (~4-5 calls uncapped in the repo evals).

## 1. Measure first (BUILT 2026-10-21)
Built: per tool turn the loop's steps used and whether it ran into its last step (`llm_turns.note_tool_loop`, from `react_loop` and `native_loop`), saved in the daily turn totals and shown on Sonic Health, Turns tab, "Does the step limit matter?" (share of tool turns that used every step, average steps, spread, deep turns on their own). Read it after a week or two of real use before changing any cap.

(Original plan:)
Add counters (closed key list in `backend/utils/self_counters.py`, no user id or text): tool turns, steps used (bucketed), turns that reached the forced final step without a final, and which tier ran. Show them on Sonic Health. Decide on any cap change from these, not from a guess.

## 2. Allowance that follows the work (BUILT 2026-10-21, undeployed: `backend/utils/library_allowance.py`)
Built differently from the sketch below in one way: the grant is the SHORTFALL, not `ceil(N / 5)` outright. Reads needed = `ceil(files / 5)` (the loops batch five per step); the grant is what the budget left does not already cover, once per turn after a successful listing, at most 4 (`LIBRARY_EXTRA_STEPS_MAX`), and none in low-power mode. So the 7-file review that fit gets nothing; on Render's budget of 4, the react loop fits 10 files and the native loop 15, and a bigger library gets the steps it needs. The model is told (a note on the listing result / a message) to read five at a time. If the budget still runs out, the reply gets an authoritative note naming the listed files that were never read. Both loops take an optional `library_allowance`; `agent_workflow` makes one per turn for people with a library. Not run against a real library with more than seven files yet (the tests use a scripted model).

(Original sketch:)
After `list_library_files` returns N files, grant `ceil(N / 5)` extra steps, once per turn, capped (about 4) and never above the tier's ceiling. Reuse the loop's existing bounded extra-step mechanism (the one steering messages use). On a forced final with unread files, the answer names what it read and what it did not.

## 3. Max tier (decided 2026-10-20)
- 12 steps (`TOOL_AGENT_MAX_ITERATIONS_MAX`, env-tunable like the others). Setting becomes three levels: standard / deep / max; the stored boolean `deep_thinking` maps to "deep" so nobody changes by accident.
- **A persistent toggle is fine** (its cost and thinking effect are visible in the menu). A one-message-at-a-time mode stays available as an option if it is ever needed.
- **Budget-gated:** low-power mode still caps at 4; refuse or downgrade when the person's remaining daily allowance is too small; the menu says it uses more of the allowance. Guests and locked accounts do not get it (existing lock lists).
- **The tier sets steps and nudges only, not the model.** The reasoning model stays whatever the Code model toggle says (`tool_agent_llm(deep, choice)`): Claude Haiku 5.5 when Claude is chosen, otherwise Gemini (3.6-flash for deep and max, flash-lite otherwise). With Claude selected, deep and normal already share one model, so deep only changes steps. Before relying on this, re-run a small targeted coding comparison (Haiku vs 3.6-flash); the saved A/B logs have no results tables.
- **A way out:** at about half the steps, a notice, "if you can answer now, answer"; uses the same mechanism as the "steps left" notice.
- **Open to everyone** (budget-gated), same metrics; no admins-only stage.
- Per-user cost already shows on Sonic Health, so the cost of the tier is visible.

## 2026-10-24 addendum: the native engine's own ceiling, and how turns end
- **The native loop has its own cap.** `native_loop.run` uses `min(requested steps, MAX_STEPS)`, and `MAX_STEPS` is `TOOL_AGENT_NATIVE_MAX_STEPS` (default 8). A Max tier of 12 (or the default deep budget of 14) is clamped to 8 on the native engine unless that variable is raised. The Render values for `TOOL_AGENT_MAX_ITERATIONS`, `TOOL_AGENT_MAX_ITERATIONS_DEEP` and `TOOL_AGENT_NATIVE_MAX_STEPS` live in Render's environment, not in the repo (the doc above says normal 4 and deep 6 there): check all three before building Max.
- **Counters for how a tool turn ends** (built, undeployed): answered by the halfway step, answered later, ran into the last step with a draft kept, ran into it with nothing written, and the halfway nudge shown / followed by a draft. They are on Sonic Health, Turns tab, under "Does the step limit matter?". They are the evidence for the checkpoint idea below.
- **Checkpoint idea (not built):** in a long budget (10 or more), at about every third of the steps the model gets a choice, answer or `continue_working(reason)`; a text reply is the final answer. Interim answers stay internal and are kept like a draft, so a turn that runs out returns the latest one. Build it if "ran out of steps with nothing written" stays above a few percent after the draft checkpoint is live.

## 2026-10-24: checkpoints BUILT (native engine only, undeployed)
- `native_loop.checkpoint_after(budget)`: for a budget of at least `TOOL_AGENT_CHECKPOINT_MIN_STEPS` (9), after a third and two thirds of the tool steps (4 and 8 of 12) the model is asked to decide: answer now, or call `continue_working(reason)` (optionally with its best answer so far in the same reply). A text-only reply is the final answer and ends the turn. On continue, the question is removed from the conversation, replaced by one short note, and the best answer so far is kept like a draft (shown back to be checked; returned, labelled unfinished, if the turn runs out). The halfway nudge is replaced by checkpoints on those turns. Not used on a turn that must end in `propose_local_edits`.
- `MAX_STEPS` (`TOOL_AGENT_NATIVE_MAX_STEPS`) default raised from 8 to 12, because 8 clamped any deep budget above it.
- Switch off to compare: `TOOL_AGENT_CHECKPOINTS=off`. Counters on Sonic Health (checkpoint turns, answered vs continued) plus the exit counters above, and the coding counters (`code_cap_hit`, `code_edited`, `code_verified`) are the outcome to compare.
- To have it run you need a budget of 9 or more: locally the deep default is 14 (so 12 after the ceiling); on Render deep was noted as 6, so raise `TOOL_AGENT_MAX_ITERATIONS_DEEP` there (and watch the spend).

## 2026-10-24: propose, wait for apply or decline, carry on (native engine, undeployed)
- `propose_local_edits` on the native engine now WAITS (no model call) for the diff card's Apply or Decline instead of ending the turn. The card posts to `POST /api/local-edits/{id}/decision`; `backend/services/local_edit_decisions.py` holds the wait (default 10 minutes, `LOCAL_EDIT_WAIT_SECONDS`; `LOCAL_EDIT_WAIT=off` turns it off; the stream is touched every 20 s so a proxy does not close it). The model then gets APPLIED (the server's copy of those files is refreshed from the validated edits, so a read afterwards sees them), DECLINED (with the reason if given) or NO DECISION, and carries on: check, fix, propose a follow-up, or finish.
- Only when the page says it can report (`edit_decisions` on the chat request), and never on the old engine, so an old cached page or the ReAct loop gets the previous behaviour with no wait.
- One server process holds the wait. With several workers a decision that lands on another one is not seen and the wait times out.
- Checkpoints on a change to a folder offer `propose_local_edits` or `continue_working`; a plain answer is not accepted as the finish.
- Cost: waiting is free, but a Claude conversation cache (about 5 minutes) is cold after a long wait, so the first step after one is billed as a fresh prompt.

## 2026-10-25: the sandbox runs in its own process (a prod crash)
- **What happened.** In prod, `run_sandbox_tests` started ("running 1 test file(s) against a copy of 449 file(s)") and about 30 seconds later the Render instance restarted with no error. The interpreter ran inside the web server; compiling the 26 MB WASI Python peaks near 430 MB and the compiled module then stays resident for the life of the server (about 220 MB). On a small instance that is an out-of-memory kill (not confirmed from Render's memory graph; it fits the log).
- **Now.** Each run is a child process (`backend/sandbox/sandbox_worker.py`, `python -I`, none of the server's environment). Measured: cold (compiling) 3.3 s and a 430 MB peak; warm (compiled cache `python-3.12.0.cwasm` next to the `.wasm`) 0.7 s and a 58 MB peak. `fetch_sandbox.py` writes the cache, so the build should run it. Before a run starts the server checks its free memory (container limit, else MemAvailable): 200 MB for a warm run, 700 MB for a cold one, otherwise the run is refused in words. A child that dies or overruns is reported and the server is untouched. `SANDBOX_TESTS=off` switches the tool off. The guest's own memory is capped at 128 MB.
- **Still in the server process:** the older `run_python` tool (`backend/services/python_sandbox.py`) loads the interpreter in-process the same way; it should move to the same worker.

## 2026-10-25: commit and push (undeployed)
- `propose_commit(message, new_branch?, branch?, open_pull_request?, pr_title?, pr_base?, pr_draft?, paths?)` shows an approval card and commits nothing until the person approves (the same card flow as the target-doc append). Approving commits through GitHub's Git Data API with THEIR OWN token (checked to have push access), onto the branch their folder is on (the browser reads `.git/HEAD` and sends `git_branch`), or onto a new branch created from it, and optionally opens a pull request. Fast-forward only, never forced; a branch that moved is refused. The message is the model's one or two sentences plus a `Co-authored-by: Sonic Assistant` trailer.
- What is committed: only files Sonic changed and the person applied (`backend/utils/applied_changes.py`, paths and counts in the person's workspace folder; every Apply is reported to the server whether or not a turn is waiting), as the synced folder holds them at approval time; the card carries an 8-character fingerprint of each file and the commit is refused if one changed after the card. Line endings follow the repo's copy. A file that differs from the approved change by more than that change gets a warning (someone else's work on GitHub would be replaced).
- Refused paths: `.github/`, secret-looking files, dependency manifests and lockfiles, Dockerfile, render.yaml, Sonic's own notes, binary and Word files. At most 10 files / 500 KB. The default branch is allowed when it is the current one, with a warning on the card.
- Refused in a turn where the agent read web pages, email, shared documents, the library or app logs (`_UNTRUSTED_CONTENT_TOOLS`): ask again in a new message.
- Code: `backend/services/git_commit.py` (GitHub calls), `backend/services/commit_flow.py` (card, parse, execute), tests with an in-memory GitHub (`backend/tests/fake_github.py`).
- 2026-10-25 (later): "commit our working changes". Nothing in the person's ledger is the normal case when the work was done outside Sonic, so `propose_commit` has `scope`: `applied` (the files Sonic changed and they applied; the default when any are waiting) or `working` (the default when none are): every text file in the synced folder that differs from the branch on GitHub, found with one recursive tree listing and local git blob hashes (no downloads; either line ending counts as the same; a file not on GitHub that the repo's root .gitignore ignores is not a change, a tracked file always is). Never swept in: `.sonic/`, refused paths, binaries, files over 500 KB (named on the card). Limits raised to 40 files / 4 MB, 500 KB each. The card warns that a file changed on GitHub since the last pull would show as reverted. A request that says commit/push/new branch is routed to the tool agent in `build_agent_plan` (`commit_flow.wants_commit`, route reason `commit_request`) even when it also says "PR": the older drafter (`_draft_create_pr`) used to take it and invented a head branch.
- 2026-10-25 (merge): after an approved commit that opened a (non-draft) pull request, the result message carries a SECOND card, "Ready to merge this pull request" (`commit_flow.merge_card`, registry entry `merge_pull_request`, own token, no role). Approving it merges through `PUT /pulls/{n}/merge` with the head sha as a guard (squash first, then the other methods if the repo disallows it); before merging it re-reads the pull request and refuses if it is closed, a draft, conflicted, or no longer has the card's branches and head commit. The commit's approval never merges anything; a plain "no" after the card merges nothing. A model-written merge card is stripped like any other forged card (`_looks_like_approval_card` covers every registered marker).
- 2026-10-25 (catch-up commands): Sonic commits through GitHub's API, so the person's own git has not seen the commit. The commit result now ends with a copyable block (`commit_flow.catch_up_after_commit`): `git fetch origin`, `git stash push -u -m ...` (nothing is thrown away), `git checkout <branch>`, and for a plain push also `git pull --ff-only origin <branch>`; then how to look at what the stash still holds and drop it. The merge result carries `catch_up_after_merge` (fetch, checkout the target, `pull --ff-only`, and an offer to `git branch -D` the merged branch, capital D because a squash merge looks unmerged). Branch names are checked again before they are printed (`_ref`); no force, no `reset --hard`, no `checkout -f`. The text is emitted as-is (action_complete cards bypass the voice composer), and the chat's code blocks already have a Copy button.
- 2026-10-25 (merge on request, better messages): `propose_merge` (pr_number or head [+ base, method]) answers "merge feat/x into main" / "merge PR 129" with the SAME merge card the commit result carries, built from the pull request as GitHub has it NOW (a card made before the branch moved is replaced, not refused). A request that starts with "merge" is routed to the tool agent (`commit_flow.wants_merge`), where before only commit-ish follow-ups were, which is why Sonic once answered "I can't merge". When NO pull request exists for the named branch, an admin gets the OLDER route unchanged: `_draft_create_pr` + `_execute_create_pr` (via `execute_write_node`) opens the pull request and squash-merges it in one approval; the card now says so. Commit messages: the model's own is kept when it says what changed; a missing, too short or generic one ("commit the working changes", "feat(x): commit working changes from local folder") is replaced by one a small model writes from the actual diff (`commit_flow.suggest_message`, with a plain "Update a.py, b.py" fallback when the model is unavailable or says nothing). The text of the change goes only to that call and is never logged.

## 2026-10-25: plan mode (opt-in, built, undeployed)
- **Why.** Multi-file edits ran out of tool steps on the read right before the diff ("re-send the request"), losing everything the turn learned; other turns never found the component and asked for a path. Evidence: Jack's mascot edits with deep thinking on.
- **What.** The "Plan first" toggle in the "..." menu (needs a connected folder; off in low-power mode). With it on, an edit request starts a read-only PLAN TURN (read tools + `submit_plan`, up to `TOOL_AGENT_PLAN_STEPS` = 12, native engine only) that ends in a stored plan: files (checked against the folder: an existing file must exist, a new one must not), ordered steps naming their files, tests, unknowns. A card in the thread: Approve and start, reword or remove a step, Cancel; typing feedback revises it, a short "yes"/"cancel" works too. Nothing is edited before approval.
- **Executing.** The approved plan is injected as data and the turn works on the first step not done. A step is DONE when an edit covering all its files is APPLIED (marked by code at the Apply report, not by the model). A turn that runs out of steps leaves the plan; "Continue" resumes at the first step not done. An approved plan is carried out even if the setting is switched off later.
- **Budget (Jack's rule).** On-plan tool steps (reading a plan file, proposing edits, running tests) are handed back to the loop's budget, so a long plan runs as long as it needs; any step off the plan (a search, listing, a read of a file the plan does not name, the web) is a deviation: `CODE_PLAN_DEVIATION_STEPS` = 3, then the loop stops and says what else it needs. A hard ceiling `CODE_PLAN_EXEC_HARD_CAP` = 30 total steps. An edit touching more than `CODE_PLAN_MAX_OFF_PLAN_FILES` = 1 file outside the plan is refused.
- **Stored.** `code_plans` (one doc per conversation, 7-day TTL, deleted by "forget everything"); only counts are logged. Counters (Sonic Health, Behavior tab): plans approved, execution turns that ran out of steps (compare with the coding-turn row), steps finished, off-plan edits refused.
- **Numbers are guesses.** Tune 12 / 3 / 30 from a week of the counters. Not built: plans for repo changes without a folder, a per-step budget, the model reading the plan's files in one batch before step 1.

## 2026-10-25: the prompt meter (built; shows on Sonic Health, Turns tab)
- **Why.** A tool turn is several model calls and each call re-sends everything before it, so the cost of a turn is its prompt size times its call count, and nobody had measured the parts. Plan mode ran at about 2% of the 5-hour budget per turn. The one number on file is a deep turn that sent about 195,000 tokens in ten calls.
- **What.** `backend/utils/prompt_meter.py`, hooked into `native_loop.run`: per tool turn, the size in characters of the instructions, the tool list, preferences, repo map, saved notes, conversation, folder/notes/plan note and the request; the model calls made; the tool results read; and the total sent across all calls. Aggregate counters (`native_*` keys), no text, no person. The card "Where a tool turn's prompt goes" shows per-turn averages with a rough token estimate (3.8 characters each).
- **Static reading before the data (from code only).** The fixed rules are about 730 tokens (+250 with a folder). All 38 native tool declarations with their own descriptions are about 4,500 tokens; `propose_local_edits` alone is about 1,000 and `propose_commit` about 700. Most tools take their description from the menu line, so the real list is larger than that figure.
- **First suspicion to test with real numbers:** the whole tool list rides on every call. The reasoner already flags what a turn needs (`needs_github_search`, `needs_gmail_lookup`, `needs_calendar_lookup`...), so a repo turn could be offered the repo, memory and edit tools only. Not built: decide from the card, and watch for flags that under-trigger.
