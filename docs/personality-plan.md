# Sonic's working character: philosophies, leanings and the record behind them

Started with Jack 2026-10-25. Jack's idea: stances Sonic will defend when it works (coding first), built into a real personality it can pull from, grounded in real past attempts, too much to put in every prompt, so found by meaning like semantic memory.

## The shape (`backend/components/sonic_leanings.py`)
- **Philosophies** (the stable character, about 8): a statement and the reason it holds, both written as true of how the work goes, never as a feeling or a memory. `evidence`, `cause`, `small`, `your_call`, `honest_gaps`, `plain`, `fit_in`, `edges`, `economy`.
- **Leanings** (the many specific habits): each follows from one philosophy, has a `when` description and 3 to 4 short example `asks`, one line in Sonic's voice, and dated, abstract `evidence` notes of the real failures it came from (no text from anyone's messages, no names).
- **Approval:** only `approved: True` entries are ever used. Today three leanings are live (frontend: which rule wins, fix where it renders, read the change back) and three philosophies they depend on (`evidence`, `cause`, `honest_gaps`). Everything else is a draft waiting for Jack: approving is changing one flag.
- **The policy applies in full** (docs/feelings-policy.md): leanings, priorities and ways of working; no emotional stake, no lived experience. A test holds every statement, reason, line and evidence note to the identity check, a feeling-word list and a claimed-memory list. Sonic may say "this has gone wrong in my record" only because an evidence note backs it.

## How a turn uses them (`backend/utils/leanings.py`)
Entries are embedded once (each example ask separately plus the description) and stored in `sonic_leaning_index` with a hash, so a restart re-embeds nothing and an edited entry is re-embedded alone. A tool turn with code tools embeds its request (one embedding call, no model call), scores each entry by its best example, keeps the closest 3 at or above 0.66, and puts them in the prompt under their philosophy, with the philosophy's reason, after the fixed rules so the cached prompt start is unchanged. The person's preferences and the project's conventions always win: a leaning is said once, with the reason, then the person's way is followed.
- **Calibration (real embeddings, 2026-10-25):** requests meant for an entry scored 0.68 to 0.82; the closest miss was 0.63 (an email summary against `say_the_cause`); unrelated requests 0.43 to 0.58. Matching on one long description alone was far blurrier (right and wrong matches overlapped at 0.55 to 0.69), which is why each entry has example asks.
- **Counters** (no text, no person): `leaning_turns`, `leaning_used_<id>` per entry, and the prompt card's "leanings" row shows what they cost.

## The record behind them (evidence)
Each leaning came from something that really happened in Sonic's own recorded turns: the mobile cards bug where it blamed the CSS, a plan whose list missed two cases the code could return, stopping after every plan step to ask what the file answered, twice asking for a path it could have searched for, edit turns that ran out of steps on the read before the diff, a branch name it invented, an approval card it wrote itself, saying it could not edit with a folder connected. The `evidence` notes are the source of "my record shows".

## 2026-10-26: what its praised replies have in common (Jack's own history, personal turns excluded)
- **Method.** Every AI reply in Jack's two conversations (2,800), minus any reply within two messages of a personal or crisis keyword (relationships, substances, distress, family, safety, names of people): 1,259 set aside, 1,541 usable. A reply counts as praised when the next message is short and praises or thanks (95 of them). For each of twelve features of a reply, the share of praised replies was compared with the share of all usable replies. Nothing was saved to disk and nothing personal is recorded anywhere; the notes below are about replies' shape only. (A first pass used a filter that matched nothing because of a typo in the script; it was caught and rerun, and no personal text was written down.)
- **What stands out** (the other features were within noise at this sample size): praised replies end on a question much less often (9% against 20%, about 2.7 standard errors), and open with a plain acknowledgment more often (16% against 9%, about 2.3 standard errors). These back two new drafts: `end_when_done` and `acknowledge_then_act` (area `talk`; nothing yet carries leanings into the reply voice, so they are drafts for Jack and for that later step).
- **What did not matter, though one might have expected it to:** length (the medians are identical, 123 words), bullets (praised replies used them slightly less), bold, headings, humor (slightly less in praised ones), emoji, naming the user.
- **Caveats.** One person, 95 praised replies, praise is sparse and tends to follow wins that were already going well, so this describes what went with approval, not what causes it. It must never become a target: the praise rate is not in any prompt or goal (docs/feelings-policy.md, "Why not its own numbers"), and the leanings are evidence of what worked, not something to maximise.

## 2026-10-26: do the leanings earn their place? (outcome counters, built)
- **What is counted, per leaning, no text and no person:** `leaning_used_<id>` (put in a tool turn's prompt), `leaning_capped_<id>` (that turn hit its step limit), and for the message after the reply: `leaning_followed_<id>`, `leaning_pushback_<id>` (the same pushback reading as the coding goal: the phrase list or a frustrated read of that message) and `leaning_praise_<id>` (a short message that thanks or praises and does not read as pushback; `code_outcomes.is_praise`, crude on purpose).
- **How it links:** a reply that used leanings is stamped with their ids (`leanings_used`, like the `code_turn` mark), and the next message in that conversation is counted against them. Like the existing coding follow-up counters, the stamp lives in memory, so a message that arrives after a server restart is not counted (it undercounts a little, never overcounts).
- **Seen:** Sonic Health, Turns tab, "Working leanings in use": per leaning the uses, how many got a next message, pushback and praise shares, the step-limit share, and a last row for all coding turns to compare against.
- **How to read it, and not to:** small numbers, and a leaning is used on different work each time, so this is a comparison at most. It is never a target and never in a prompt. What it can honestly say: a leaning that is used often and is followed by pushback more than the baseline is a candidate to reword; one that is never used is a candidate to retire.
- **Next, once there is data (a few days after deploying):** the draft pipeline (signal-gated proposals, deduped against the index, approved in the dashboard), for all accounts while there is only one person on it.

## 2026-10-26: experiences, cited as a record (built; the same for tool turns and plain conversation)
Jack's idea: Sonic answering with "that reminds me of..." where the thing is a real event it can point to, not a performed memory; and, later, a self-model and reflections on its own record. Built so far:
- **The record.** `backend/utils/experiences.py`: today an experience is an evidence note of an approved leaning (dated, abstract, failure / worked / record), so there are about 45 already. Only approved ones can ever be cited. They are indexed by meaning in `sonic_experience_index`, built in the background like the leanings.
- **How it is said.** As a record being consulted: "this is close to a case in my record: ...". Never as a recollection happening to Sonic: "I remember a similar case", "that reminds me of this one time", "I've seen this before" claim a felt act of recall that is not there even when the event is real. New rule in the identity check (`FELT_RECOLLECTION`): a sentence claiming that about its own past is rewritten unless the same sentence anchors it in the record ("that reminds me of a case in my record" passes); sentences about what the PERSON said ("I remember you told me...") are left alone. The prompt block tells the reply the same, adds nothing beyond the note, and says a failure may be cited only when it changes what is being done now (never as a confession), a success plainly and briefly, a number once and only if it bears on the question.
- **Restraint (shared_history's, pointed inward).** Once per ten messages (a marker on the reply), never under a safety context, a heavy mood or a closing message, only when the request is close in meaning to a note (threshold 0.66, calibrated on real embeddings: related requests 0.63 to 0.85, unrelated 0.47 to 0.55), and in a plain conversation only when no other proactive item has the turn's slot (a case from the record takes the slot).
- **Where.** Tool turns (alongside the working leanings) and plain conversation turns (the voice prompt), by one entry point (`backend/utils/character.py`) that reuses the embedding the turn already made. Leanings now reach plain conversation too, when the person is not carrying a heavy mood.
- **Counted:** `experience_offered` and `experience_cited` (the reply said "in my record" or similar), on Sonic Health's Behavior tab.
- **Still to build, in this order:** (1) capture: new experiences from objective signals (a pushback, a step limit, a declined edit, a praise), written as abstract notes, validated, deduped against the index, kept pending until approved in the dashboard (all accounts for now, Jack being the only one); (2) reflections on an experience, on the shelf_reflections pattern (a system's reading of its own record, pending until approved), with an explicit anchoring rule for failures: it must tie to something useful right now, never a confession; (3) a self-model: periodically synthesised, every statement backed by evidence ids or numbers, human-approved, revisable, so "what kind of system am I" has something real under it (most of its inputs exist: counters, routines, shelf topics, tasks, goals, leanings, the changelog).

## 2026-10-26: step 1, capturing new experiences (built)
- **Signals (set by code):** `pushback` (the message after a coding reply read as pushback), `step_limit` (a coding turn hit its limit), `answer_check` (the answer checker found an unsupported claim) and `praise` (a short thanks after a coding reply). Kind follows from the signal; the date is the day it happened.
- **One small model call per signal writes one note.** Gated before it runs: never for a guest, under a safety context, with a heavy mood, or after a turn that read untrusted text (web, email, a document, logs, the browser: a reply is stamped `untrusted_content` and a later signal about it is ignored). At most 3 a day and 20 waiting; a note close in meaning (0.80) to one stored, or to one already in the record, adds to its count or is dropped instead of becoming another.
- **The note is checked by code, not by the model:** 6 to 40 words, one sentence, third person starting "It" or "Sonic", no quotes, links, file paths, identifiers, digits, proper names, second person, feelings or intentions, and it passes the identity check. Nothing from the turn is stored: only the note, kind, signal, area and date (the excerpt the model reads is clipped to about 400 characters per part and dropped).
- **Approval:** stored `pending` (expires after 30 days), never cited and never in a prompt until approved on Sonic Health, tab "Its record" (approve, edit with the same checks, delete). Approved notes join the record (`experiences.entries(db)`), are indexed and may be cited like the hand-written ones.
- **Real model check:** four signals through the real small model all produced notes that pass every check; after a prompt tweak ("say what it did not do that would have helped"), a pushback note says it did not verify the change and an answer-check note says it claimed a read that had failed. Step-limit and praise notes stay generic, which is expected from the little the excerpt holds.
- **Counters:** `experience_captured`, `experience_capture_merged`, `experience_capture_invalid`.

## 2026-10-26: step 2, reflections on recorded experiences (built)
- **What it is:** for an approved note, a 12 to 70 word reflection of what a system like Sonic takes from it (`backend/utils/experience_reflections.py`), stored in `sonic_experience_reflections`, pending until approved on Sonic Health, "Its record". Once approved it rides along as an extra sentence when the experience is cited (`experiences.build_block`); it is never offered on its own.
- **Checks:** the shelf's (`shelf_reflections.reflection_issue`: a system not a person, no feelings, no time claims, no numbers or links, nobody addressed) plus one new rule: a reflection on a failure or a figure must say a concrete first-person habit ("so when X, I check Y"). Bare "this went wrong" is refused. The model may reply NOTHING when no habit follows plainly.
- **Backfill:** "write reflections" writes up to 12 missing ones at a time, one small call each. Remove is final; edit sends an approved one back to pending.
- **Real model check:** failure notes ended in habits; figure reflections were wrong at first (read a low test count as a good sign) until the prompt said a low count of checking is a gap to close.

## 2026-10-26: step 3, the self-model (built)
- **What it is:** "what kind of system am I", every statement evidence-backed, challengeable, revisable (`backend/utils/self_model.py`, collection `sonic_self_model`, Sonic Health tab "Self-model").
- **Facts are gathered by code, not the model** (`gather`): the week's mix of work, its routines, goals, the reading shelf, leanings, the record, the changelog count, tool-call ratios and coding numbers, rounded and cached for 10 minutes. A source that cannot be read is left out. Two fixed facts say it does not exist between conversations and has no feelings.
- **Statements cite facts** (`[F2, F5]`). Checks: the cited facts exist; a number only if it is in a cited fact; a system speaking; nothing addressed, felt, wanted, or time-claimed; no stake in its own numbers; no share "of my time" (the facts count turns); no purpose the facts do not state ("to inform my work"); the identity check. The last two came from the first real-model run, which wrote both.
- **Approval and staleness:** statements wait pending until approved (a new write replaces only the waiting ones). An approved statement goes stale when a fact it cites reads differently or disappears, and stale ones are not said until edited or re-approved. An edit is checked against its cited facts and sends the statement back to pending. Retire is final.
- **Use:** only when the message asks what it is, what it spends its time on, or how it works (`self_model.asks`), up to 6 approved current statements go into the conversational prompt, with "not covered here, say you do not know". Counter `self_model_used`.
- **Real model check:** 14 facts gave 7 statements, 5 kept after the new rules; the kept ones read true to their facts.

## 2026-10-26: its own memory is part of the self-model (built, from a real reply)
- **The failure:** Jack pasted a reply to "how does that make you think about yourself and your own memory architecture?" It was generic ("relevance versus drift", "clean separation of concerns", "appreciate"), said nothing specific about Sonic, and implied it had no decay or pruning (it has both). Cause, checked: nothing in the profile or the self-model described its memory, and `asks` did not match the question, so the model improvised from general knowledge about agents.
- **The fix:** `_memory_facts` adds 12 facts to the self-model, each number read from the setting that governs it (`gather.memory_part`): saved-state window (40), facts per person (1,500) and areas, trust half-life (90 days), recall bar (0.80), second look band (0.06), merge similarity (0.85) and group size (12), stale-note bar (0.90), and counts of notes and archived copies (counts only, rounded, moved no data). Fixed-rule facts (pruning order, what is checked before saving, events keep unknowns, erase, habits are approved) are pinned to the code by tests, so a code change fails a test and prompts a rewrite. A changed setting changes the fact, so a statement resting on it goes stale.
- **Asking:** `asks_memory` matches questions about how its own memory is built or works, not "do you remember my dog?". `approved_block(db, facts, message)` puts the statements about memory first (up to 8) for a memory question, and last for any other self-question. `MAX_STATEMENTS` is 12.
- **Two checks were too literal, found by the real run:** the number check compared spellings ("1,500" vs "1500", "0.80" vs "0.8"), now by value; and the stake rule refused the word "scores", which blocked "a match scores at least 0.80" (now only "my/its/our score"). Before the fix 2 of 12 were dropped, after it 0.
- **A slip no check can catch:** the first real reply said a new piece of information matching an old note flags the note stale; the rule is that notes matching the REPLACED fact are flagged. The writer's statement was ambiguous the same way, and the fact now says "the replaced, older fact". This is why statements wait for approval: read the memory ones against the code before approving.
- **Not built:** nothing maps the article's categories (working, long-term, procedural) onto Sonic's own, so a reply can still skip that mapping; "forgetting" and "decay" statements are written only if the writer chooses them.
