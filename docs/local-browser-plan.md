# A local browser for Sonic, through the runner (built 2026-11-01, uncommitted, no real model has used it yet)

Asked 2026-11-01 (Jack): can Sonic see the person's `localhost` pages with its browser tool? Today it could not; "let's do 2" (the bigger option below) was the answer, and "yep one approval works lets do it" approved the preview-session design. This is the write-up, as the runner itself had one (docs/local-runner-plan.md).

## Build status (2026-11-01, undeployed, runner 0.2.0 untagged)
**Phases A0, A, B and C are built and tested; D (clicking, typing, scrolling, emulation beyond size) and E (a real-model check) are not.**

- **First live use (Jack, 2026-11-01, on SAAPP's own app at localhost:8080) found two things.** (1) A REAL BUG, fixed the same day: `--host-resolver-rules=MAP * ~NOTFOUND , EXCLUDE localhost` also applies to IP literals, so every look at `http://127.0.0.1:...` (and `[::1]`) failed with ERR_NAME_NOT_RESOLVED. The rule now excludes `localhost`, `127.0.0.1`, `[::1]` and `::1`; regression tests open every spelling against a real browser; and a lookup failure is no longer reported as "is the server running?" (2) A LIMIT, by design: SAAPP's own frontend loads the Clerk script from clerk.accounts.dev, which a look blocks, so the page stays on "Loading session...". Sonic read the blocked-host list correctly. Apps that need an outside script to render cannot be looked at as they are. Possible fix, not built and Jack's call: a per-computer allow list in the runner's own config file (`~/.saapp-runner/config.toml`, never from the server or the project) naming the outside hosts a person accepts a page contacting, shown on the card, off by default; it would weaken "nothing leaves the machine" only for hosts the person names. Also seen: the card showed as a generic "Run look" card because the server on :8080 was serving an older frontend build (local/dist has the new card; `app.py` does not serve dist, so something else serves :8080).

## Why it cannot today
- Sonic's browser tool (backend/services/browser_tool.py) is a CLOUD browser (browserless.io over CDP). It sees the public internet only, so `localhost` on a person's computer is unreachable. The server's page reader (backend/services/url_reader.py `check_url_allowed`) refuses loopback and private addresses on purpose, so the server can never be made to fetch an internal address.
- The runner (runner/, `saapp-runner`) refuses web addresses in a command (commands.py: "Web addresses are not allowed in a command") and blocks `curl`, `wget` and the other network programs. It only connects OUT and never listens on a port.
- A prompt with the word "browser" goes to the OLD engine (native_loop.needs_old_engine), where the cloud browser lives. The native loop has no browser tool.

## What it is
A new kind of runner job, **`look`**: open ONE page on the person's own machine in a hidden (headless) browser, in a window size they choose (phone, tablet, desktop), and send back what it looks like and what is wrong with it. Sonic asks for it with a native tool, `look_at_local_page(url, device)`; the person approves each look on a card, exactly as for `run_local_check`; the runner does it and answers.

**What comes back (phase 1, read-only):** a screenshot, the page title and final address, the visible text (capped like command output, 6,000 characters), console errors and warnings (capped), local requests that failed or returned 4xx/5xx, and layout facts that answer the usual mobile bug without a model: whether the page is wider than the window (horizontal overflow) and which few elements stick out. The screenshot is described by the vision model that already reads attachments, so Sonic gets words AND the facts. No clicking or typing in phase 1.

## The browser: the person's own Chrome or Edge, over the DevTools protocol
- **Nothing to download.** Windows always has Edge; most people have Chrome. The runner finds an installed Chrome, Edge or Chromium (fixed install paths, then `PATH`), and reports in its hello which one it found (`browser: "edge" | "chrome" | null`), so the server only offers the tool when there is one. No Playwright (about 150 MB of its own browsers, and the runner stays standard-library only).
- **A throwaway profile.** Started with `--headless=new --user-data-dir=<a fresh temp folder> --remote-debugging-port=0`, so it has none of the person's cookies, logins, extensions or history; the folder is deleted afterwards. It reads `DevToolsActivePort` for the loopback port it was given and talks CDP over a WebSocket. The runner needs a small WebSocket client of its own (the standard library has none): about 150 lines, tested against a fake server and against the real browser.
- **Why CDP and not `chrome --screenshot`:** only CDP can ENFORCE "this machine only" (next section) and read the console, the failed requests and the layout. The flag form follows redirects off the machine.

## Safety: what the runner enforces, whatever the server sends
The same rule as for checks: the server proposes, the runner decides. A job names a page; it never carries a command or a program.
1. **Loopback only.** The URL must be `http://localhost`, `http://127.0.0.1` or `http://[::1]`, a port from 1 to 65535, an ordinary path, no credentials (`user:pass@`), no other scheme (`file:`, `chrome:`, `data:`, `javascript:`, `view-source:`). Checked by the runner on every job, even one the server handed out, and never the runner's own server address.
2. **Nothing leaves the machine while the page loads.** CDP request interception (`Fetch.enable`): every request whose host is not loopback is FAILED, including redirects, scripts, fonts, images and analytics, and including IP literals. The page cannot phone out and cannot be used to reach another machine on the person's network (a `192.168.x.x` address is not loopback either).
3. **A time limit and a size limit.** Page load, quiet period, total run (15 s default), screenshot size (a capped JPEG, about 600 KB), text and lists capped. The browser process tree is killed on timeout or cancel, as `execute.py` already does for checks.
4. **Approval first, every look.** The card says what will happen: "Sonic wants to open http://localhost:5173/ in a hidden browser on your computer, phone size. The screenshot and the page's text will be sent to Sonic and its AI model." Run and Cancel. Nothing runs before Run.
5. **The person's browser is never touched:** no visible window, no existing profile, no other tab, no access to anything but the one page.

## Privacy
A screenshot of the person's own app goes to the SAAPP server and to the vision model's provider, which the card says. It is stored with the job for the job's retention (7 days) and shown to the person on the card, never put in logs, never written to memory or the experience record (it is a tool result: it joins the untrusted-tools lists like command output, so a page that contains instructions cannot cause a commit or an edit in that turn). The page's text is labelled data in the result, as command output is.

## Server side
- **Job kind `look`** in backend/utils/runner_jobs.py, beside `check` and `command`: `create_look_job`, validated here too (the same URL rules, so a bad address never becomes a card), `LOOK_SINCE = (0, 2, 0)` gating like `COMMANDS_SINCE` (an older runner would refuse it as "no such check"), `WANTED_RUNNER_VERSION` moves to 0.2.0.
- **The result** carries the screenshot as base64 (capped) next to the text fields; `api_result` accepts and bounds it; a new authenticated endpoint serves it to the card. `format_result` writes the data block Sonic reads (title, address, text, console, failures, layout facts) with the vision description.
- **The tool** `look_at_local_page(url, device)` in native_tools.REGISTRY, offered only when the page can show its card (`runner_cards`), the person is signed in, exactly one runner is connected and new enough, and it reported a browser. Not batchable, refused on a plan turn, an untrusted-tool. It waits on the card like `run_local_check` (`wait_for_result`), cancels the job if the turn is stopped, and returns `format_result`.
- **Routing.** When the tool is offered, a message about "my page" or "the browser" stays NATIVE (the way `test_runs_native` keeps "run the tests" native). The old engine's cloud browser stays for public pages.
- **Vision call.** One call on the model that already describes attachments, with a prompt for UI review (what is visible, what looks broken or cut off, no guessing at what is not shown). It is an extra model call, so low-power mode refuses a look with a plain reason, and it is counted (below).
- **Steps and combos.** A look is a CHECK, like a test run: after an applied edit it counts as the verification the claim check wants for a visual claim ("fixed the overflow"), and a look that shows the problem is still there is a counter-hit under backend/utils/combo.py, not a landed action. It costs one tool step.
- **Counters (counts only):** `look_offered`, `look_run`, `look_failed` (by reason: no browser, refused address, timeout, cancelled), `look_after_edit`, `look_found_problem`.

## The card and Settings
- **The card** (`LookCard.tsx`, in the style of RunnerCheckCard): address, device, the exact sentence about what is sent, Run and Cancel, then Stop while it runs, then the screenshot, the title, and the console and layout lines. A phone-width screenshot sits in a phone-shaped frame.
- **Settings** (Account, the runner card): "Browser: Edge found" or "No Chrome or Edge found: install one to let Sonic look at your local pages".

## Starting the dev server (asked 2026-11-01: "would this allow it to run npm run dev to visually check things like you do?")
**Not by itself, and not with `run_local_command` as it is.** That tool already exists (Sonic proposes a line, the person approves, the runner runs it), but the runner gives every command a time limit and kills the whole process tree when it passes or when the command ends, and a dev server never ends: it would run until the limit, be killed, and the page would be gone before the next look. What is missing is a **managed background process**, the equivalent of what my own preview tool does with a named server:
- **Named servers, found by the runner like checks** (presets.py): `npm run dev` or `npm start` from the folder's `package.json` scripts (and later `flask run`, `uvicorn`, `python -m http.server` when the project says so). Sonic asks for one BY NAME (`start_local_server("dev")`), never supplies a command, as with `run_local_check`.
- **The runner keeps it running** in the background, one per project, with its output in a small ring buffer (last few KB), and finds the port from the output ("Local: http://localhost:5173/", "ready on :3000", "Running on http://127.0.0.1:5000") with a time limit for it to say so. It reports `running`, the port and the last output lines; a server that exits early reports the exit code and its last lines (so Sonic reads the real error, like a failed check).
- **Stopping:** a Stop button on the card, a tool call `stop_local_server`, an idle limit (stopped after 30 minutes with no look or request), when the runner stops or updates, and when the person removes the project. The whole process tree is killed, as `execute.kill_tree` does for checks. The runner's own start-up also clears any server it left behind.
- **Same trust as running tests:** `npm run dev` runs the person's own project scripts on their machine, so it asks first, with the exact command on the card, and the server's port is shown. It is NOT exposed by the runner: the runner still listens on nothing; whether the dev server itself binds to the network is the person's own configuration (the card says "listening on 127.0.0.1" or warns "listening on all addresses (your network can reach it)" when the output says so).
- **Then `look` works on it** (the address must still be loopback and, with a managed server, the port is the one the runner reported, which is what keeps Sonic from pointing a look at some other local service).
- **A preview session instead of a click per look (proposed upgrade to the earlier decision):** the edit-then-look loop needs many looks. ONE approval covers "start the dev server for this project and look at it while Sonic works on this change": up to 10 looks of that server's loopback address, until the session is stopped, goes idle (30 minutes) or ends. Each look still shows its screenshot on the card, with a Stop button, but takes no click. Starting any OTHER server or looking at any other address is a new card.

## Phases
- **A0. Managed servers in the runner** (before or with A): presets for `dev`/`start`, the background process, port detection, ring buffer, stop, idle limit, tests with a real stand-in server process (a tiny script that prints its port, runs, and is really dead after Stop), kill-on-runner-exit.
- **A. The runner (no server):** URL rules, browser finder, WebSocket client, CDP session, the `look` action with interception, layout facts, limits; tests: the rules as a table (every bad URL), the WebSocket client against a fake server, interception proved against a REAL browser (skipped when none is installed; this Windows machine has Edge), kill-on-timeout, nothing leaves loopback (a local page that links to a second local server on another port is allowed, one that links out is blocked).
- **B. The server and the tool:** job kind, version gate, result with the screenshot, endpoint, tool, routing, vision description, counters; tests with a scripted model and a thread playing the person and the runner, as for `run_local_check`.
- **C. The card and Settings,** looked at in a browser at phone and desktop widths in both themes.
- **D. Interactions (a separate decision):** click, type, scroll, wait for text, and device emulation (touch, user agent, pixel ratio), under ONE approval for a bounded session (for example up to 8 actions on one page, all on loopback), with the card showing each step as it happens and a Stop. Not before phase 1 has been used on real pages.
- **E. A small targeted eval** on real models, with Jack's go-ahead and spend discipline: does Sonic pick the right address and device, wait, and report what the screenshot shows without more than it shows?
